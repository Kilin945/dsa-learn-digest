本週主題：雜湊表（Hash Table）——一種把「找東西」改成「算位置」的資料結構。
先自己想答案，再往下翻到「—— 解答 ——」對照。想不出來沒關係，先寫下猜測，對照時記憶最深。
Q1（概念與應用）
雜湊表（Hash Table）把資料的「鑰匙」（key）用一個公式算成「桶子編號」（桶 = 陣列裡的一格，用來放資料），之後想找資料，直接算一次就知道去哪格。請用你自己的話說：為什麼這樣平均來說比「從頭一個一個找」快？它換來速度的代價是什麼？
Q2（概念與應用）
你要處理三件事：(a) 只想知道「這個帳號有沒有註冊過」；(b) 要統計每個關鍵字出現幾次；(c) 要依「加入的先後順序」列出所有項目。Java 裡有 HashSet（只存鑰匙、用來判斷有沒有）、HashMap（鑰匙配一個值）、LinkedHashMap（會記住加入順序的 HashMap）、TreeMap（鑰匙會自動排好序、可查區間）。這三件事各該選誰？如果第四件事是「找出 100～200 之間的所有編號」，又該選誰？
Q3（概念與應用）
「衝突」（collision）是指兩個不同的鑰匙被算到同一個桶子。如果一個設計很差的雜湊函式讓大部分資料都擠進同一個桶，查找會變得怎樣？用「一間只開一個窗口的銀行」類比說說看。
Q4（概念與應用）
有人寫了一個雜湊函式：「把字串每個字元的編號加總」。請問「listen」和「silent」這兩個字（字母一樣、順序不同）會怎樣？這個做法在什麼情況下會讓系統越來越慢？Java 的 String.hashCode 是怎麼避開這個問題的？
Q5（概念與應用）
「負載因子」（load factor）= 元素數 ÷ 桶子數，代表桶子有多擠。Java 預設門檻是 0.75，超過就會自動擴容。請說明：(a) 為什麼不等到桶子全滿才擴？(b) 擴容時為什麼「每一筆資料都要重新算位置」？(c) 偶爾發生一次很慢的擴容，為什麼整體還是說每次操作平均 O(1)？（O(1) = 不管資料多少，花的時間大致不變。）
Q6（實作與複雜度）
Java 的 HashMap 算桶子編號時，用的是 (h ^ (h >>> 16)) & (n - 1)，而不是 h % n（h 是 hashCode，n 是桶數）。(a) 這個寫法什麼條件下才等同取餘數？(b) 因此 HashMap 怎麼處理你指定的容量？(c) 先把 h 與「自己右移 16 位」做 XOR（^，相同為 0、不同為 1）有什麼好處？
Q7（實作與複雜度）
開放定址法（open addressing，衝突時不外掛串列，而是在陣列裡往後找空格）搭配線性探查（一格一格往後看）。桶數 8，雜湊函式 h(key) = key % 8，依序插入 3、11、19，再刪除 11，最後查找 19。(a) 三個鑰匙各放在哪格？(b) 若刪除 11 時直接把那格清成「空」，查 19 會發生什麼事？(c) 正確做法是什麼？
Q8（實作與複雜度）
LeetCode 128「最長連續序列」：給一組無序整數，求最長的連續數字段長度（例如 [100,4,200,1,3,2] 答案是 4，因為 1,2,3,4），要求 O(n)。(a) 把所有數字放進 HashSet 後，為什麼只從「連續段的起點」（即 x-1 不在集合裡的數）往後數？(b) 為什麼這樣總時間是 O(n) 而不是 O(n²)？(c) 對這個例子追蹤：哪些數字會被當成起點？
—— 解答 ——
Q1　一個一個找，資料越多越慢；雜湊表是直接「算」出位置，不管多少筆，平均只算一次，所以平均 O(1)。代價：要多花空間（桶子要留空位）、要處理衝突、要擴容，而且 key 要守紀律（見 Q4、本週 hashCode／equals 的規則：相等的物件 hashCode 必須相同，且 key 放進去後內容不能亂改）。

Q2　(a) HashSet；(b) HashMap（鑰匙＝關鍵字，值＝次數）；(c) LinkedHashMap；第四件「找區間」選 TreeMap，因為雜湊表只擅長「精確找某一個」，不保留大小順序。

Q3　全擠一個桶＝所有人排同一個窗口，查找得一個個比對，退化成 O(n)（資料越多越慢），雜湊表的優勢就沒了。

Q4　「listen」和「silent」字母相同，加總一樣 → 算出同一個桶，撞在一起。字母組成相近的資料很多時（例如大量換位字），全擠同桶，查找退化成 O(n)。String.hashCode 用 h = 31×h + 字元，每走一步先乘 31，所以「位置」也會影響結果，換位後數字不同。但要記得：衝突只能減少、不能消除；hashCode 相同也不代表 equals 相同，最後仍靠 equals 確認是不是同一個 key。

Q5　(a) 桶子越滿衝突越多，速度就掉，所以要留空位，在 75% 左右就擴。(b) 桶數變了（例如 16→32），公式用的 n 變了，同一個 key 算出的桶子編號也可能不同，所以每筆都要重新分桶（rehash）。(c) 一次擴容雖是 O(n)，但每次擴容桶數翻倍，擴容很少發生；把成本平均分攤到每次插入，每次只多一點點，這叫「攤還」（amortized）分析，結果仍是 O(1)。

Q6　(a) 只有 n 是 2 的次方時，& (n-1) 才等同 % n（例如 n=16，n-1 的二進位是 1111，剛好留下最低 4 位）。(b) 所以 HashMap 會把你給的容量補成「最接近的 2 的次方」（例如指定 10 → 16）。(c) 只留低位時，高位的資訊會被丟掉；先把高 16 位混進低 16 位，高位不同的 key 也能分散開，減少衝突。

Q7　(a) 3%8=3 → 放第 3 格；11%8=3 被佔，往後 → 第 4 格；19%8=3，3、4 都被佔 → 第 5 格。(b) 若把第 4 格清成「空」，查 19 時從第 3 格看到不是，再看第 4 格是空 → 誤以為「不存在」就停了，但 19 其實在第 5 格，查不到。(c) 刪除時放「墓碑」（tombstone，標記「這裡曾有資料，繼續往後找」），查找遇墓碑要繼續，遇真正的空格才停。

Q8　(a) 若 x-1 在集合裡，x 就不是起點，從它數會重複走別人已走過的路；只從起點數，每一段連續數字只會被數一次。(b) 每個數字最多被「當起點判斷」一次、被「往後數」一次，總共約 2n 次、每次集合查找平均 O(1)，所以 O(n)；若每個數都往後數則可能 O(n²)。(c) 集合 {100,4,200,1,3,2}：100（99 不在）、200（199 不在）、1（0 不在）是起點；4、3、2 的前一個都在，不是起點。從 1 數 1→2→3→4 長度 4；100 長 1；200 長 1；答案 4。
