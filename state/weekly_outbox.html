📗 每週回顧 · DSA · 2026-10-30

這週我們都在學同一件事：雜湊表（hash table，一種用「key 算出位置」來快速存取資料的結構）怎麼處理「兩筆資料搶同一個位置」的問題，還有它怎麼維持速度。下面 7 題請先自己想，再看最後的解答。前 4 題用日常語言就能答；後 3 題需要一點程式與複雜度的概念。

Part 1 · 概念與應用題（人人可答）

Q1. 想像一棟有 16 個信箱的公寓，要塞進 100 封信。為什麼「兩封信被分到同一個信箱」（這叫雜湊衝突 hash collision）是一定會發生、不是誰寫錯了？

Q2. 處理衝突有兩大類做法：鏈結法（chaining）與開放定址（open addressing）。請用白話說明各自遇到衝突時怎麼做。

Q3. 負載因子（load factor）＝ 放了幾筆 ÷ 有幾個桶子。它在衡量什麼？Java 的 HashMap 預設超過多少會「擴容」？擴容後桶子變多少？為什麼要這樣做？

Q4. 你要把剛好 1000 筆資料一次放進 HashMap。如果什麼都不設定，會發生什麼事讓程式變慢？有什麼辦法預防？另外，把容量開成 100 萬又有什麼壞處？

Part 2 · 實作與複雜度題（偏工程）

Q5. 開放定址（衝突時往後一格一格找空位，叫線性探查 linear probing）裡，桶子 3、4、5 都有資料。現在把桶 4 的資料刪掉，如果直接把桶 4 改回「空」，之後查桶 5 的那個 key 會發生什麼事？正確的做法是什麼？

Q6. Java HashMap 的桶數固定取 2 的次方（例如 16）。請說明：(a) 為什麼可以用 (n-1) & hash 取代 hash % n？(b) 為什麼還要先做 h ^ (h >>> 16)？(c) 擴容成 32 時，一個元素要不要搬家，只看哪一個位元？

Q7. (a) Java 8 的 HashMap 在什麼條件下會把一條鏈結串列改成紅黑樹（一種自動保持平衡的搜尋樹）？最壞查詢時間從什麼變成什麼？(b) 為什麼 hashCode 相同、又不能互相比大小的 key 仍會讓它退化？(c) 擴容單次 O(n)，為什麼每次 put 的攤銷（amortized，把偶爾一次的大成本平均分攤到每次操作）成本仍是 O(1)？

—— 解答 ——

A1. 因為 key 的可能數量遠多於桶子數（鴿籠原理：100 封信放 16 個信箱，至少有信箱裝 7 封以上）。衝突是數學上必然，不是 bug，所以重點是「發生後怎麼處理」。

A2. 鏈結法：每個桶子後面掛一條鏈結串列（linked list，一個接一個的清單），衝突的資料排在同一條後面。開放定址：不掛清單，這格被佔了就往後找下一個空格放。前者速度看「最長那條鏈」，後者要小心資料擠成一團。

A3. 它衡量雜湊表有多擁擠，越擁擠衝突越多、越慢。Java 預設門檻 0.75，超過就把桶數翻倍，並重新計算每個 key 該去哪個桶（rehash）。目的是把擁擠程度壓回去，維持平均 O(1)。

A4. 不設定會從小容量開始，一路擴容、一路搬家（rehash），浪費時間。預防：初始容量設 n ÷ 0.75 + 1（約 1335），一次到位。注意容量參數是「桶數」不是「元素數」。開 100 萬則白白佔用大量記憶體。

A5. 直接清成空：查桶 5 的 key 時，從它的雜湊位置往後找，走到被清空的桶 4 就停，誤判「不存在」，但資料其實在桶 5。正確做法是放墓碑（tombstone，標記「這裡曾有資料，繼續往後找」）。另外線性探查會有「聚集」現象，連續被佔的格子越來越長。

A6. (a) n 是 2 的次方時，n-1 的二進位全是 1，AND 運算等於取 hash 的低位元，等同取餘數但更快，也不會出現負數。(b) 遮罩只看低位元，高位元的差異會被忽略，所以先把高 16 位元混進低位元，讓分布更均勻。(c) 翻倍後多出一個位元：該位元是 0 留在原桶，是 1 就搬到「原桶號 + 舊桶數」。

A7. (a) 單一桶的鏈長到 8，且桶數至少 64，改成紅黑樹；最壞從 O(n) 降到 O(log n)。(b) 樹需要比大小才能排序；hash 相同又比不出大小，就只能逐一比對，退化回接近 O(n)。所以樹只是保險，hashCode 仍要寫好（這也有助防範 hash flooding：刻意製造大量衝突的攻擊）。(c) 每次擴容翻倍，前面所有插入的搬家成本加總約 2n，平均到 n 次 put，每次只多出常數成本，所以攤銷 O(1)。
