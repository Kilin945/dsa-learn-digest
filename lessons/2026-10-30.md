## 雜湊衝突：鏈結法 chaining 與開放定址 open addressing · 第 4 步

### Chaining's Worst Case: When a Chain Gets Too Long

![鏈式位址雜湊表](https://raw.githubusercontent.com/krahets/hello-algo/main/zh-hant/docs/chapter_hashing/hash_collision.assets/hash_table_chaining.png)

圖：[Hello 算法](https://www.hello-algo.com/) · CC BY-NC-SA 4.0

鏈式位址（separate chaining）把每個桶裡原本的單一元素換成一條鏈結串列，鍵值對是串列節點，所有發生衝突的鍵值對都儲存在同一條串列中。因此哪個桶的串列最長，查那個桶就最慢。

**鏈越長，查得越慢**

查 key 時先算桶號，再沿該桶的串列從頭比對。鏈長 L 最壞要比 L 次，所以是 O(L)（串列不能直接跳到中間）。最極端是 n 筆資料全擠同一個桶，整個雜湊表退化成一條串列，查詢 O(n)。

**Java 的補救：長鏈變成樹**

Java 8 起，某個桶的鏈長到達 8 且桶總數至少 64 時，會把那條鏈改成紅黑樹（treeify），該桶最壞查詢降為 O(log n)。桶總數不足 64 時改為先擴容；樹縮到 6 個節點以下會變回串列。

**樹只是保險，不是主力**

分布均勻且負載因子在 0.75 以下時，鏈長到 8 的機率極低（約千萬分之六），多數桶的鏈只有 0～2 個節點。HashMap 平常快靠的是均勻分布與負載因子，樹化只是防壞情況。

> ⚠ 最容易搞錯：HashMap 內部不是樹，主體仍是陣列加鏈結串列，只有被擠爆的桶才樹化；樹化後最壞是 O(log n)，仍比正常的 O(1) 慢。

一句話：鏈結法的速度取決於最長那條鏈；Java 在鏈長到 8 時把它改成樹，把最壞情況從 O(n) 壓到 O(log n)。

### 這東西用在哪

**對寫程式的人**：自訂 key 時 equals() 與 hashCode() 要成對寫好，hashCode() 要分散。若永遠回傳同一個數，所有物件進同一個桶，查詢會從 O(1) 掉到 O(log n)（有樹化時）甚至更差。資料量大時 HashMap 莫名變慢，先懷疑 hashCode() 分布不均。

**對產品端的人**：依帳號查資料、檢查 email 是否註冊、快取，背後常是雜湊表。健康的雜湊表在資料長到十倍時速度幾乎不變；若查詢隨資料量成正比變慢，值得問工程師為什麼。若 key 可被使用者操控，攻擊者能造出大量衝突（hash flooding）拖慢伺服器，樹化是 Java 的緩衝。

### 動手寫 · LeetCode

[#706 Design HashMap](https://leetcode.com/problems/design-hashmap/)（Easy）

**題目在說什麼**：不能用內建 HashMap，自己做一個支援 put、get（查不到回 -1）、remove，key 與 value 都是整數。

**怎麼用今天學的東西解**

1. 準備 769 個桶（質數），每個桶是一條鏈結串列。
2. 雜湊函式用 key % 769。
3. put：走訪該桶，找到相同 key 就覆蓋，否則加在尾端。
4. get：走訪該桶，找到回傳 value，否則 -1。
5. remove：從該桶移除 key 相同的節點。

**複雜度**

- 時間：平均 O(1)，最壞 O(n)。每次操作要走訪一條鏈，平均鏈長約 n/769；全擠同一桶時要走 n 個節點。
- 空間：O(n + 769)。每筆資料一個節點，加上固定 769 個桶。

```java
import java.util.*;

class MyHashMap {
    private static final int N = 769;
    private LinkedList<int[]>[] table;

    public MyHashMap() {
        table = new LinkedList[N];
        for (int i = 0; i < N; i++) {
            table[i] =
                new LinkedList<>();
        }
    }

    // 雜湊函式：key 對桶數取餘數
    private int idx(int key) {
        return key % N;
    }

    public void put(int key, int val) {
        int h = idx(key);
        for (int[] e : table[h]) {
            if (e[0] == key) {
                // key 已存在，覆蓋 value
                e[1] = val;
                return;
            }
        }
        // 沒找到，掛到這條鏈後面
        table[h].add(
            new int[]{key, val});
    }

    public int get(int key) {
        int h = idx(key);
        for (int[] e : table[h]) {
            if (e[0] == key) {
                return e[1];
            }
        }
        return -1;
    }

    public void remove(int key) {
        table[idx(key)]
            .removeIf(e -> e[0] == key);
    }
}
```

### 今日術語表

| 術語 | 中文 | 定義 |
|---|---|---|
| Treeify | 樹化 | 鏈長到 8 且桶數至少 64 時，把鏈結串列改成紅黑樹，最壞 O(log n) |
| Red-black tree | 紅黑樹 | 自動保持平衡的二元搜尋樹，操作皆 O(log n) |
| Worst case | 最壞情況 | 最倒楣輸入下的所需時間，例如所有 key 撞進同一桶 |
| Hash flooding | 雜湊洪水攻擊 | 刻意造出大量同桶 key，讓雜湊表退化拖慢伺服器 |
| hashCode() | 雜湊碼方法 | Java 物件回傳整數，HashMap 用它決定桶號 |
