## 迭代與遞迴：兩種重複的形式、呼叫堆疊與尾遞迴 · 第 3 步

### Call Stack & Recursion Depth（呼叫堆疊與遞迴深度）

程式執行函式呼叫時，電腦需要記住「現在算到哪、等一下要回去哪裡」，這塊記憶體區域叫呼叫堆疊（call stack）。每呼叫一次函式，堆疊上就多疊一個「堆疊幀（stack frame）」，裡面存著這次呼叫的區域變數、參數與返回位置，直到這次呼叫真正返回後才會被釋放。

迭代（for/while 迴圈）每輪只是重複用同一組變數更新，不會多疊堆疊幀；但遞迴每呼叫自己一次，就會在還沒返回前多疊一層，這是遞迴通常比迭代更耗記憶體的原因。

以 `recur(n) = n + recur(n-1)` 為例，呼叫 `recur(5)` 要等 `recur(4)` 返回、`recur(4)` 要等 `recur(3)` 返回……一路等到觸底。觸發終止條件前，同時存在的呼叫層數就是「遞迴深度」，深度越深，同時占用的記憶體就越多。

⚠ 最容易搞錯的地方：有終止條件不代表就沒事——只要輸入的 n 本身夠大，遞迴深度一樣會變深，一樣可能塞滿呼叫堆疊、丟出堆疊溢位（stack overflow）。堆疊溢位的根本原因是「同時疊著的堆疊幀太多」，跟有沒有終止條件是兩件事。

```java
// 每次呼叫都會佔用一層堆疊幀空間
static int recur(int n) {
    // 終止條件：觸底不再往下呼叫
    if (n == 1) return 1;
    // 遞迴呼叫：呼叫時多開一層堆疊幀，等這層回傳才能算
    int res = recur(n - 1);
    return n + res;
}
```

### 這東西用在哪

- 對工程師：遞迴深度若會隨輸入資料量線性增加，就該改寫成迴圈，避免 StackOverflowError；深度固定或很淺時遞迴通常更好讀。
- 對產品端：聽到「遞迴實作」的巢狀功能（組織圖、巢狀資料夾、巢狀留言），可以問「巢狀深度有沒有上限」——遞迴深度失控通常是直接當機，不是慢慢變慢。

### 動手寫 · LeetCode

[#1342 Number of Steps to Reduce a Number to Zero](https://leetcode.com/problems/number-of-steps-to-reduce-a-number-to-zero/)（Easy）

題目：給非負整數 num，偶數除以 2、奇數減 1，重複到 0，問要幾步。

解法：把「還要走幾步」定義成遞迴函式，終止條件 num==0 回傳 0，其餘每次遞迴呼叫並把這一步算進去；呼叫堆疊上疊的高度正好等於答案步數。

複雜度：時間 O(log n)（偶數步驟每次讓 num 減半，跟位元數成正比）；空間 O(log n)（遞迴深度跟著步驟數成長，每層都占用一份堆疊幀）。

```java
class Solution {
    public int numberOfSteps(int num) {
        // 終止條件：已經歸零，不用再走
        if (num == 0) return 0;
        // 偶數：除以二；奇數：減一
        int next = (num % 2 == 0) ? num / 2 : num - 1;
        // 遞迴呼叫，並把這一步計入
        return 1 + numberOfSteps(next);
    }
}
```

### 今日術語表

- **Call Stack（呼叫堆疊）**：記錄函式呼叫關係與返回位置的記憶體區域。
- **Stack Frame（堆疊幀）**：每次函式呼叫時新增的一份記錄，存著區域變數、參數、返回位置。
- **Recursion Depth（遞迴深度）**：觸發終止條件前同時存在的呼叫層數。
- **Stack Overflow（堆疊溢位）**：呼叫堆疊被塞滿、超過記憶體上限時的錯誤，Java 中為 StackOverflowError。
